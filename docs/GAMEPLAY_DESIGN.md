# Rack & Ruin — Core Gameplay Design

**Document status:** Core gameplay authority  
**Version:** 0.1  
**Design type:** Single-player pool roguelite / precision strategy game  
**Target platform:** Steam for Windows and Steam Deck first  
**Working title:** Rack & Ruin  

> This document defines the game that should be built. When implementation details, future ideas, or individual content concepts conflict with this document, this document wins until it is deliberately revised.

---

## 1. Product Definition

### 1.1 One-sentence pitch

**Rack & Ruin is a turn-based pool roguelite where the player builds a machine of cues, chalks, and table rules, then executes precise billiards shots to create impossible scoring chains.**

### 1.2 Player promise

Every turn should give the player a meaningful question:

> “What is the highest-value shot I can deliberately create with the table, my build, and the remaining shots—and can I execute it?”

The game must satisfy both halves of that promise:

- The player must make real spatial and timing decisions.
- The player must be able to build a strategy that changes which shots are valuable.

It is not a standard pool simulator with random items attached. It is not a card game represented by pool balls. Pool physics, table geometry, cue-ball control, and ricochets are the primary verbs.

### 1.3 Launch product

The initial release is a focused premium single-player game:

- One polished roguelite run mode.
- One practice table.
- Multiple difficulty stakes.
- Seeded challenge support after the main run is stable.
- Keyboard/mouse and controller support.
- Steam Cloud, achievements, Steam Input, and Steam Deck support.
- No real-time multiplayer at launch.
- No microtransactions.
- No requirement for an online connection after Steam authentication has been attempted.

### 1.4 Design pillars

1. **Billiards mastery**  
   The player understands and improves at angles, power, spin, banks, cue-ball placement, and multi-ball collisions.

2. **Build-defining rules**  
   Items create new shot incentives and tradeoffs. They do not merely increase damage or score.

3. **Readable risk**  
   The player sees enough information to make an informed decision, but not so much automation that execution disappears.

4. **Fast, expressive turns**  
   Planning is deliberate; resolution is exciting and brief; the next decision arrives quickly.

5. **Scenario-first puzzle tables**  
   Most encounters begin from authored tactical situations assembled from tested modules, so the player solves a meaningful table position rather than merely clearing a random rack.

6. **Replayable variety without chaos**  
   Runs vary through seeded layouts, encounters, rewards, and table rules, while identical inputs in identical states always resolve identically.

## 2. Terminology

| Term | Definition |
|---|---|
| **Run** | One attempt beginning at the opening rack and ending in victory or defeat. |
| **Tour** | The complete map progression of one run. |
| **Encounter** | One table challenge on the map. |
| **Rack** | The set of balls currently active in an encounter. |
| **Shot** | One confirmed cue-ball action and its complete resolution. |
| **Turn** | Synonym for shot in player-facing text; code should use `Shot` consistently. |
| **Foul** | A rules violation that applies a penalty. |
| **Scratch** | The cue ball enters a pocket or otherwise leaves the playable table. |
| **Bank** | A target ball reaches a rail before entering a pocket. |
| **Kick** | The cue ball reaches a rail before contacting its first target ball. |
| **Combination** | A target ball contacts another target ball before the scored pocket event. |
| **Carom** | One ball causes another ball to move or be pocketed through a collision chain. |
| **Contract** | The encounter’s required objective. |
| **Chalk** | A trigger-based run item that alters scoring, rules, or resources. |
| **Cue** | A run item that alters shot capability or shot economy. |
| **Table Modifier** | A run item or encounter rule that changes table geometry or physics. |
| **Tag** | A standardized property such as `BANK`, `COMBO`, `SPIN`, or `POSITION`. |
| **Shot Quality** | The set of tags and events generated by a resolved shot. |
| **Cash** | The spendable currency inside a run. Lost when the run ends. |
| **Reputation** | Persistent unlock currency. It never directly increases a live run’s power. |
| **Stakes** | Persistent difficulty tiers that add rules and improve rewards. |
| **Seed** | The deterministic identifier used to reproduce a run, encounter, and reward sequence. |
| **Planning phase** | The phase in which the player aims, changes spin/power, inspects rules, and confirms a shot. |
| **Resolution phase** | The phase in which the shot simulation runs and results are presented. |

## 3. Core Player Experience

### 3.1 The complete moment-to-moment loop

```text
Inspect table
  → choose a scoring intention
  → aim and set shot parameters
  → confirm shot
  → deterministic physics resolution
  → evaluate shot tags and contract progress
  → collect score/rewards/penalties
  → inspect changed table
  → choose the next shot
```

The loop must be short enough that the player can take several shots per minute, but rich enough that a strong player thinks about cue-ball position and future geometry.

### 3.2 Encounter loop

```text
Enter encounter
  → read objective and table rules
  → take shots within the shot budget
  → satisfy contract
  → receive score, cash, and reward choices
  → choose the next map node
```

### 3.3 Run loop

```text
Start with basic loadout
  → route through map
  → win encounters
  → buy and choose build pieces
  → adapt to elites and events
  → defeat regional boss
  → advance stake or unlock content
```

### 3.4 Desired emotional rhythm

Each encounter should move through these beats:

1. **Read:** “What is this table asking me to do?”
2. **Plan:** “Which line creates the most value?”
3. **Commit:** “I know the risk; take the shot.”
4. **Payoff:** “The balls are chaining exactly as intended.”
5. **Adapt:** “The table changed; what is my next line?”

A miss should usually produce an understandable lesson:

- too much power;
- insufficient angle;
- poor cue-ball placement;
- a risk that was visible but accepted;
- a build interaction misunderstood and then explained.

The game must avoid unexplained misses caused by invisible margins, inconsistent pocket behavior, or item triggers that are difficult to inspect.

### 3.5 Scenario-first encounter philosophy

Rack & Ruin is scenario-first rather than rack-first. The majority of encounters begin with an authored tactical situation: a barrier blocks a line, a physics zone changes a route, a pocket is locked, a target is trapped, or a sequence must be solved. The player still uses normal pool actions, but the table asks a specific puzzle question.

The game contains three encounter families:

- **Scenario Tables:** the primary encounter family. These are assembled from authored, validated modules and contain a deliberate tactical setup.
- **Open Tables:** conventional pool layouts used for pacing, recovery, economy, and build expression without a complicated puzzle rule.
- **Boss Tables:** highly authored multi-phase scenarios with unusual geometry or rules.

Target launch distribution:

- 65% Scenario Tables;
- 20% Open Tables;
- 15% elite, event, and boss tables with advanced scenario rules.

A Scenario Table must have:

1. A readable starting position.
2. One primary tactical question.
3. At least two viable solution families.
4. A visible relationship between the scenario and the encounter contract.
5. A failure that teaches the player something.
6. A meaningful interaction with multiple build archetypes.
7. A deterministic, finite resolution path.

Scenarios are not miniature logic puzzles that happen to contain balls. Every solution must use recognizable billiards verbs: direct shots, banks, kicks, combinations, caroms, spin, cue-ball placement, pocket choice, or deliberate sacrifice.

## 4. Billiards Simulation Rules

### 4.1 Table geometry

The initial production table is a standardized rectangular pool table with six pockets:

- four corner pockets;
- two side pockets;
- rounded or chamfered pocket mouths represented consistently in the simulation;
- six rails divided into named segments for modifier effects.

The logical table uses normalized coordinates so gameplay is resolution-independent:

```text
Playable width: 1.0 logical units
Playable height: 2.0 logical units
Ball radius: 0.028 logical units
```

The rendered table may use any aspect-preserving visual size. The simulation must never depend on screen pixels.

### 4.2 Balls

Every ball has:

- unique ID;
- ball archetype;
- position;
- velocity;
- angular/spin state;
- pocketed state;
- target status;
- color/pattern identifier;
- base value;
- tags;
- optional encounter-specific state.

The cue ball is always a separate entity and is not a target unless an explicit rule says so.

### 4.3 Ball archetypes

The first release should support these archetypes:

| Archetype | Default behavior | Design purpose |
|---|---|---|
| **Standard** | Normal mass, friction, and value | Baseline readability. |
| **Heavy** | Lower response to collisions and spin | Changes power and bank planning. |
| **Light** | Higher response and longer roll | Rewards controlled low-power shots. |
| **Wild** | Value or tag changes after a defined event | Creates adaptable targets. |
| **Anchor** | Resists movement or cannot be pocketed until unlocked | Creates geometry and obstacle puzzles. |
| **Prism** | Changes value/tag based on first contact type | Encourages specific shot patterns. |

New archetypes must have a clear visual symbol in addition to color.

### 4.4 Physics model

The simulation is gameplay-oriented, not a promise of professional tournament realism. It must prioritize:

- repeatability;
- readable collision outcomes;
- stable multi-ball chains;
- controllable spin;
- reliable pocket detection;
- deterministic results.

Configurable parameters include:

- ball radius;
- mass by archetype;
- rail restitution;
- ball restitution;
- rolling friction;
- sliding friction;
- spin transfer;
- spin decay;
- pocket capture tolerance;
- minimum movement threshold;
- maximum shot speed;
- maximum simulation duration.

The simulation uses a fixed time step. A shot is complete only when all active balls are below the rest threshold or the maximum resolution time is reached.

If the simulation hits the maximum resolution time, it must safely settle remaining balls using a deterministic fallback rather than hanging or producing a partial result.

### 4.5 Aiming and shot parameters

A shot contains:

```text
origin cue-ball position
angle in radians
power from 0.0 to 1.0
spin_x from -1.0 to 1.0
spin_y from -1.0 to 1.0
called pocket, if the encounter requires one
```

Default power thresholds:

- `0.00–0.08`: no shot; confirmation is disabled.
- `0.08–0.30`: soft.
- `0.30–0.65`: medium.
- `0.65–0.90`: hard.
- `0.90–1.00`: maximum.

These labels are player-facing guidance, not separate physics modes.

The default aim guide shows:

- cue-ball travel line;
- first collision prediction;
- projected target-ball direction;
- pocket target line when appropriate;
- optional rail preview unlocked by a cue or accessibility setting.

The game must support a reduced guide for players who want more execution challenge. It must not remove the ability to understand active rules.

### 4.6 Spin

Spin is selected on a cue-ball diagram:

- vertical axis: top spin / backspin;
- horizontal axis: left/right side spin.

Spin effects are intentionally readable:

- **Top spin:** cue ball continues forward after contact.
- **Backspin:** cue ball pulls backward after contact.
- **Side spin:** changes rail rebound and collision angle.

Extreme spin should increase execution risk. Spin does not guarantee a desired outcome; it modifies the result within the physics model.

### 4.7 Legal contact

Unless an encounter rule overrides it, the first ball contacted by the cue ball must be a valid target.

A valid target is:

- any standard target in a normal encounter;
- the currently required ball in an ordered encounter;
- a specific ball type defined by the contract;
- an explicitly permitted non-target under a table modifier.

A shot is legal if the cue ball contacts a valid target before any invalid target or rail-only sequence.

### 4.8 Pocketing

A ball counts as pocketed when its center crosses the pocket capture boundary and it is moving toward the pocket. Once pocketed, it is removed from the active simulation and emits one `ball_pocketed` event.

A ball that rolls over a pocket mouth but does not cross the capture boundary remains active. The result must be consistent and visually understandable.

Each pocket has:

- ID;
- type: corner or side;
- base value multiplier;
- current lock/open state;
- optional modifier tags.

### 4.9 Scratch and cue-ball recovery

A scratch occurs when:

- the cue ball enters any pocket;
- the cue ball leaves the playable surface;
- a table modifier explicitly marks the cue ball as lost.

Default scratch result:

- the shot is resolved normally up to the scratch event;
- all pocketed target balls remain pocketed;
- the player receives a foul;
- one additional shot is removed from the encounter budget;
- the cue ball is placed at the designated recovery point;
- the next planning phase begins with a brief scratch indicator.

The default recovery point is the center of the table unless a contract or modifier defines a ball-in-hand zone. The player does not receive unrestricted ball-in-hand placement in the base game.

A cue, Chalk, or encounter rule may alter scratch consequences, but the result must be shown before the shot is taken.

### 4.10 Shot termination

A shot ends when:

1. all balls are at rest;
2. the maximum resolution time is reached and the fallback settles the table;
3. an encounter-ending condition is met and the game has captured the final result.

The game must never allow a second shot while balls are still moving.

## 5. Shot Evaluation and Scoring

### 5.1 Shot event log

Every shot creates an immutable evaluation record:

```text
shot_index
input_parameters
starting_positions
ending_positions
first_contact
rails_contacted
balls_pocketed
scratch
fouls
shot_tags
base_score
bonuses
penalties
final_score
triggered_items
contract_progress_delta
```

This record drives UI, replay/debug tools, achievements, and balance analysis.

### 5.2 Shot tags

The initial tag vocabulary is:

- `DIRECT`: target reaches a pocket without a rail contact.
- `BANK`: target contacts one or more rails before pocketing.
- `KICK`: cue ball contacts a rail before first target contact.
- `COMBO`: a target ball contacts another target before pocketing.
- `CAROM`: a secondary collision contributes to a pocket event.
- `MULTI_POCKET`: two or more target balls are pocketed in one shot.
- `SPIN`: meaningful spin affected the shot result.
- `POSITION`: cue ball ends in a marked or favorable zone.
- `CLEAN`: legal shot with no foul, scratch, or invalid contact.
- `CALLED`: called pocket/condition was satisfied.
- `RISKY`: shot used an encounter-defined high-risk feature.
- `NEAR_MISS`: target entered a near-pocket state but was not pocketed.

A shot may have several tags simultaneously.

### 5.3 Base scoring

Each target ball has a base value. Initial values:

- Standard: `10`.
- Light: `12`.
- Heavy: `15`.
- Wild: `10` before its state changes.
- Anchor: `20` once legally pocketable.
- Prism: `10` plus its current state bonus.

Default shot score:

```text
base_score = sum(ball_values)
              + 3 × rails_used_by_scored_targets
              + 5 × secondary_target_contacts
```

The score is then modified by multipliers:

```text
final_score = floor(
  (base_score + positional_bonus + contract_bonus)
  × combo_multiplier
  × shot_quality_multiplier
  × active_item_multiplier
)
```

Default multipliers:

- no combo: `1.00`;
- two target balls pocketed: `1.25`;
- three target balls: `1.60`;
- four or more: `2.00` maximum from base combo alone.

Shot quality multiplier:

- clean direct: `1.00`;
- clean bank or kick: `1.10`;
- clean bank plus combo: `1.20`;
- called contract success: additional `1.10`;
- foul: `0.75` unless the encounter says otherwise;
- scratch: `0.50` unless the encounter says otherwise.

These are starting values for playtesting, not untouchable constants.

### 5.4 Score clarity

The result panel reveals the score in a consistent order:

1. balls pocketed;
2. shot tags;
3. base score;
4. combo multiplier;
5. item triggers;
6. contract bonus/penalty;
7. final score.

The player should be able to answer “why did I get this score?” in under five seconds.

### 5.5 Encounter scoring target

Each encounter has a target score or completion condition. The target is chosen from a difficulty budget, not arbitrary hand tuning.

Default target bands:

- Standard early encounter: `80–120`.
- Standard mid encounter: `150–240`.
- Standard late encounter: `260–420`.
- Elite encounter: `350–650`.
- Boss phase: `500–900`, combined with a special rule.

The actual target depends on the number of available shots, target balls, and active modifiers.

## 6. Encounter Rules

### 6.1 Encounter structure

Each encounter defines:

```text
encounter_id
region
node_type
seed
rack_definition
shot_budget
contract_type
contract_parameters
base_rules
table_modifiers
reward_table
cash_reward
failure_penalty
```

### 6.2 Shot budget

The default budget is the number of confirmed shots available, not the number of balls.

Initial budgets:

- early standard: `8–10` shots;
- mid standard: `7–9` shots;
- late standard: `6–8` shots;
- elite: `7–10` shots with stronger rewards;
- boss: `10–14` shots across phases.

A shot that scratches consumes the normal shot plus the scratch penalty shot. If no shots remain after a scratch, the encounter ends in failure after the result screen.

### 6.3 Contract types

#### Score Target

Reach the required score before the shot budget expires.

Success: score is at or above target after any shot.  
Failure: shot budget reaches zero below target.

#### Clear Rack

Pocket all required target balls.

Success: every required target is pocketed.  
Failure: shot budget reaches zero.

#### Bank Contract

Complete a number of bank-tagged pocket events.

Success example: `3 BANK shots`.  
Failure: shot budget reaches zero.

#### Combo Contract

Reach a combo threshold in one or more shots.

Success example: one `MULTI_POCKET` shot with at least three target balls.

#### Precision Contract

Complete the encounter with a maximum number of fouls/scratches.

Success example: score target with zero scratches and no more than one foul.

#### Order Contract

Pocket required targets in a specific sequence.

An incorrect target contact applies a foul and does not advance the sequence. The sequence is shown beside the table.

#### Pocket Contract

Use specified pockets or avoid specified pockets.

The active pocket requirement is always visible on the table and in the contract panel.

#### Survival Contract

Reach a score threshold before a hazard counter reaches its limit.

Each shot increments the hazard counter, with special rules changing its growth.

### 6.4 Encounter modifiers

Encounter modifiers are rules attached to a particular table. They are separate from the player’s persistent run items but use the same event system.

Initial modifier set:

- **Narrow Corner:** corner pocket capture tolerance reduced.
- **Wide Side:** side pockets have increased capture tolerance and value.
- **Bumper Rail:** one rail has increased restitution.
- **Dead Rail:** one rail absorbs more speed.
- **Locked Pocket:** a pocket opens after a specified contract event.
- **Moving Target:** one marked target relocates after each successful shot.
- **Return Policy:** the first ball pocketed each shot returns after resolution.
- **Heavy Air:** all balls lose speed faster.
- **Slippery Felt:** all balls retain speed longer.
- **No Free Lunch:** every scratch removes two shots instead of one.
- **Called Table:** only called-pocket successes receive full value.
- **Hot Corner:** a marked pocket’s value increases after each legal success.

Modifier text must include a concrete example where ambiguity is possible.

## 7. Scenario Tables and Modular Generation

### 7.1 Purpose

Scenario Tables provide the game’s strongest distinction from ordinary pool. They create the equivalent of a tactical chess position while retaining continuous billiards physics. A scenario is a deliberately constructed starting state, not a pile of random modifiers.

The player should be able to look at a table and form a sentence such as:

- “I need to open the center before I can reach the valuable pocket.”
- “The cue ball is trapped, so I need a kick or a controlled escape.”
- “This bank is difficult now, but the physics zone makes it possible if I use low power.”
- “I can take the safe low-value route, or attempt the three-ball chain before the gate closes.”

### 7.2 Scenario layers

A generated scenario is assembled in layers, in this order:

1. **Table shell** — standard pool table or a bounded shape variant.
2. **Primary objective** — the contract or tactical question.
3. **Anchor module** — the main authored challenge, such as a barrier, trapped ball, locked pocket, or required sequence.
4. **Support modules** — one to three compatible rails, zones, targets, or secondary rules.
5. **Ball layout** — authored spawn sockets filled with compatible ball archetypes.
6. **Build interaction hooks** — tags and rule opportunities that allow multiple Cue/Chalk archetypes to contribute.
7. **Difficulty pressure** — shot budget, pocket constraints, hazard escalation, or a secondary objective.
8. **Validation and repair** — solvability tests and deterministic rejection of bad assemblies.

The generator must never begin by scattering random objects and hoping a puzzle emerges.

### 7.3 Authored module primitives

Every module is a reusable data asset with a local coordinate frame, compatibility tags, and validation rules.

#### Geometry modules

- **Rail Extension:** adds a short internal or external rail that preserves a recognizable pool silhouette.
- **Divider:** separates part of the table until a condition is met.
- **Gate:** a barrier that opens, closes, or moves after a defined event.
- **Blocker:** a fixed post, wall, or bumper that obstructs a direct route.
- **Channel:** a narrow passage that rewards power and angle control.
- **Clipped Corner:** removes or reshapes one outer corner while retaining a pocket relationship.
- **Central Island:** a bounded obstacle that creates bank and kick routes.
- **Pocket Mouth Variant:** changes one pocket’s effective width or angle.
- **Temporary Rail:** appears or disappears at a phase or shot threshold.

#### Physics-zone modules

- **Ice:** increased travel distance and slower speed loss.
- **Mud:** increased speed loss.
- **Elastic:** stronger collision/rail rebound.
- **Dead:** sharply reduced movement after entering.
- **Spin Well:** increases the effect of spin.
- **Spin Dead:** suppresses spin.
- **Value Lane:** grants a bonus if a scored ball crosses it.
- **Drift Field:** applies a bounded, predictable directional influence.

#### Tactical state modules

- **Trapped Cue Ball:** the initial cue-ball position has no direct legal route to the obvious target.
- **Protected Target:** a valuable ball is shielded by a blocker or Anchor ball.
- **Chain Setup:** balls begin aligned for a potential combo, but the line is fragile.
- **Sacrifice Ball:** one ball can be intentionally used to open a route or trigger a rule.
- **Pocket Sequence:** specified pockets must be used in an order.
- **Moving Target:** a target changes socket after a valid shot.
- **Hazard Ball:** an object creates a penalty if pocketed or disturbed incorrectly.
- **Split Objective:** two or more contract paths are presented, such as safe score versus difficult bonus.

### 7.4 Shape mutations

The outer table shape may change, but only through bounded, authored mutations. The game must remain visually and mechanically recognizable as pool.

Permitted launch mutations:

- clipped or blocked corners;
- an inset pocket;
- one extra internal rail;
- a narrow channel;
- a central island or divider;
- a temporary barrier that changes the playable shape for one phase;
- a boss table that combines two or three of these.

Arbitrary polygonal tables, continuously deforming boundaries, and fully irregular silhouettes are out of scope for the first release. They create disproportionate complexity in aiming, rail prediction, collision debugging, art readability, and scenario validation.

Shape mutations are weighted toward elite, event, and boss nodes. Standard Scenario Tables should usually preserve the outer rectangle and create distinction through internal modules, zones, and starting states.

### 7.5 Scenario assembly contracts

Each scenario asset defines:

```text
scenario_id
family
region_range
difficulty_budget
allowed_table_shells
anchor_module
support_module_tags
required_spawn_tags
forbidden_module_tags
contract_templates
solution_families_required
minimum_open_routes
maximum_hazard_count
build_archetype_hooks
visual_readability_notes
```

Each module defines:

```text
module_id
module_type
local_geometry
compatibility_tags
incompatibility_tags
required_clearance
required_ball_sockets
required_solution_tags
difficulty_cost
validation_rules
```

The generated scenario is valid only if all local and global constraints pass.

### 7.6 Solution families

The generator must track solution families, not just geometric reachability. A valid scenario should normally support at least two of these:

- direct precision route;
- bank route;
- kick route;
- combo/carom route;
- spin/position route;
- controlled sacrifice route;
- contract-specific pocket route.

A solution family is considered available if a deterministic solver or authored test shot demonstrates a legal path that satisfies the primary objective within the intended shot budget. The solver does not need to find the player’s exact shot; it needs to reject obviously one-line or impossible assemblies.

### 7.7 Seeded generation pipeline

Scenario generation uses deterministic named random streams:

1. Select scenario family from the encounter node and region.
2. Select a compatible anchor module.
3. Select support modules within the difficulty budget.
4. Select a table shell and orientation.
5. Place sockets and balls from the anchor’s authored layout.
6. Fill compatible ball archetypes.
7. Select a contract that matches the available solution tags.
8. Apply encounter and run modifiers.
9. Run validation.
10. Reject and regenerate if validation fails.
11. Store the final scenario seed and assembly ID for replay/debugging.

Randomness chooses among authored possibilities. It does not invent untested geometry.

### 7.8 Scenario validation

Every generated scenario must pass:

- all balls spawn without overlap;
- cue ball has at least one legal first action;
- required targets are physically reachable or have a defined unlock path;
- required pockets are not fully blocked unless the contract provides a way to open them;
- no barrier creates an accidental sealed region;
- all zones have valid boundaries;
- the shot budget is compatible with the contract;
- at least two solution families remain available where required;
- no module violates another module’s clearance or compatibility rule;
- the table can always reach a rest state;
- the scenario is reproducible from its seed.

Validation has two levels:

- **Structural validation:** fast checks for overlap, containment, tags, sockets, and legality.
- **Gameplay validation:** bounded search using simplified candidate shots, authored proof shots, and reachability analysis.

A scenario that fails validation is never shown to the player. It is rejected, repaired using a declared fallback, or replaced with a known-good scenario from the same family.

### 7.9 Quality tiers

Scenario assets are authored and reviewed in tiers:

- **Tier A:** core scenarios, manually playtested across several builds and stakes.
- **Tier B:** approved variations of Tier A modules with bounded randomization.
- **Tier C:** experimental scenarios used only in internal testing until they earn approval.

The game should prefer a smaller pool of excellent scenario families over a large pool of technically valid but repetitive or frustrating layouts.

### 7.10 Scenario examples

#### The Gatehouse

A blocker prevents a direct line to a high-value pocket. A side pocket is open, but using it closes the nearest rail for the next shot.

Possible solutions:

- bank around the blocker;
- use a Heavy or Sacrifice ball to open the gate;
- take the safe side-pocket route and pursue the lower contract;
- use spin to preserve cue-ball position for a second attempt.

#### The Frozen Lane

A Value Lane crosses the center of the table, but an Ice zone makes balls retain speed. The player must control power to pass through the lane without losing the target to a far pocket.

Possible solutions:

- low-power position shot;
- bank through the lane;
- use a Spin Well or Brake-style Cue;
- ignore the bonus and complete the safe score contract.

#### The Locksmith’s Sequence

Three pockets begin locked. Each lock opens only after a bank, kick, or called-pocket success. The rack contains a protected target and a clear low-value route.

Possible solutions:

- solve the locks in order;
- use a combination to unlock multiple states;
- accept lower score and complete a safe partial contract;
- exploit a Cue that reopens one pocket.

#### The Trap

The cue ball begins behind a Central Island. A direct shot is illegal, but two rails create a kick route. A Hazard Ball sits near the easiest pocket.

Possible solutions:

- kick to the required target;
- use a controlled sacrifice to move the Hazard Ball;
- take a scratch-saving Chalk effect and attempt a high-value line;
- use a spin route around the island.

### 7.11 Scenario difficulty

Difficulty should increase by adding one new decision at a time:

- early: one anchor module, no more than one support module;
- mid: one anchor plus two support modules, or one shape mutation;
- late: multiple interacting modules with a clear primary rule;
- elite: unusual geometry or a high-risk secondary objective;
- boss: phase changes, shape changes, or rule combinations that have been individually taught earlier.

Do not raise difficulty by stacking many unreadable rules. A hard table should be difficult because its decisions and execution are demanding, not because its rules are hidden in a paragraph.

### 7.12 Scenario-first reward hooks

Scenario Tables should affect reward selection through tags:

- bank-heavy scenarios increase the weight of `BANK` Chalks;
- physics-zone scenarios increase the weight of `SPIN`, `POSITION`, or `CONTROL` items;
- sequence scenarios increase the weight of `PRECISION` and `CALLED` items;
- barrier scenarios increase the weight of `KICK`, `COMBO`, and `RISK` items.

This is weighted relevance, not guaranteed reward. The player should feel that the run responds to the problems they are facing without removing surprise.

## 8. Run Map and Route Progression

### 8.1 Tour layout

A standard run contains four regions and a final boss:

```text
Opening → Region 1 → Region 2 → Region 3 → Region 4 → Final table
```

Each region contains:

- 5–7 map layers;
- 3 visible route choices at most decision points;
- one regional boss or gate encounter;
- at least one shop opportunity;
- at least one non-combat event opportunity.

The player sees the next 3–5 nodes on the map. Exact encounter parameters may be hidden, but node type and reward class are visible.

### 8.2 Node types

| Node | Purpose | Default result |
|---|---|---|
| **Standard** | Reliable progression and cash | One encounter, normal reward. |
| **Elite** | High risk and build-defining reward | Harder encounter, premium reward. |
| **Shop** | Spend cash and edit build | Items and one or more services. |
| **Rest** | Recover or improve one item | Choose one limited service. |
| **Event** | Tradeoffs and narrative/mechanical experiments | Choice with immediate consequence. |
| **Challenge** | Optional special objective | High variance reward. |
| **Treasure** | Build acceleration | One item or resource with a drawback if necessary. |
| **Boss** | Region gate and archetype test | Multi-phase encounter and major reward. |

### 8.3 Map fairness

The generator must guarantee:

- a playable opening route;
- at least one shop before each boss;
- at least one ordinary encounter before the first elite;
- no mandatory sequence of three elite nodes;
- a minimum cash floor for a player who wins ordinary encounters;
- no route where the player can be locked out of all rewards or recovery.

The run generator uses a seed and validates the generated map before presenting it.

### 8.4 The House's Terms (run contracts)

Before the first table, every normal run signs one of four terms. The term is
baked into the run (and its save) beside vault perks, and appears in the map's
build sheet and the table's cue line. Dailies always use THE MARK, so the shared
board stays fair.

| Term | Edge | Cut |
|---|---|---|
| **THE MARK** | The untouched game. | None. |
| **THE BANKER** | Banked pots pay +60%; +18 bank pay and +2 per cushion. | One fewer shot per table; direct pots score 25% less. |
| **THE COLLECTOR** | Multi-ball pots pay +60%; +8% combo pay. | One fewer shot per table; single pots score 20% less. |
| **THE GRIFTER** | +40 opening cash; +20 cash per cleared table. | One fewer shot per table; scratches cost an extra shot. |

The terms are not difficulty labels: they change which shot is worth taking.
A Banker routes through cushions, a Collector builds clusters, a Grifter buys
an early piece and accepts a thinner budget. The last signed term is focused on
the choice screen and remembered across sessions. The opening table keeps its
10-shot floor under every term, so a new player never learns on a shortened
lesson.

### 8.4.1 THE HOUSE'S WAGER (route stake)

Cash is normally a one-way spend: it buys pieces in shops and otherwise sits
idle. The wager gives it a second use at the moment that matters — the commit
before a rack.

| Rule | Behaviour |
|---|---|
| Where | Any scored route table: standard, elite or boss. Not shops or events. |
| Stakes | OFF, 20 or 50 run cash, chosen on the route rail. |
| Standard odds | A clear returns 2× the stake (the stake back plus even money). |
| Elite / boss odds | A clear returns 3× the stake. The House gives worse odds where it expects to win. |
| Timing | The stake leaves the wallet when the rack starts, not when the preview opens. Reading a card or backing out of a boss intro is free. |
| Loss / walk-out | The House keeps the stake. Quitting a live rack forfeits it; the pause card says so before the click. |
| Daily / ladder | Disabled. Their racks are shared, so cash must not buy an advantage. |
| Feedback | The live brief appends `WAGER n` to the shot line, the reward header names the payout, and the defeat summary names a lost stake. |

The decision is deliberately legible: the rail states the exact return before
the break, the stake is one of two fixed chips, and the wager never touches the
contract. A player can always take the safe line; a confident player can make
the same rack pay for the next shop. This also gives the House a way to win
without adding a new rule to the table: the bet is settled by the contract the
player already read.

### 8.5 THE GRIND (endless mode)

THE GRIND is the arcade alternative to the tour. It has no map, no shops, no
signed term and no House's Favor: the player is dealt a procedural rack, clears
it, takes one of three build pieces, and is dealt the next rack until the line
breaks. The mode lives on the title, opens a rules card with the saved record,
and starts from table one every time.

| Table | Rule |
|---|---|
| 1–4 | Clear contract, three targets, ten shots; the ask grows as the budget tightens. |
| 5, 10, 15… | **Gate:** an elite score contract (80 + 5 × table) in eight shots, with double foul cost. |
| Every clear | Reward room, one piece from three; the build carries across the whole run. |
| Par beat | One extra shot is banked for the next rack only. Overachieving now buys breathing room; it never compounds into a permanent budget. |
| Pace chase | The best run's cumulative score after each cleared rack is saved as a pace split. A replay shows `PACE +n` / `PACE -n` at every table, or `PACE CLEARED` once it passes the old depth. |

The pace split is snapshotted when a run starts, so a player races the record
they began against rather than their own improving run. A shorter run never
shortens the board; a deeper run, or an equal-depth run with a higher final
score, replaces it. The daily ladder keeps its own pace board and clears it at
midnight with the day's other records.

Endless racks are capped against the live rack's active targets, use the
standard procedural generator, and reset House Heat per table. A lost rack ends
the run immediately and records the deepest table and high score in local meta;
the record is banked on every clear, not only at the end, so a closed portal tab
still keeps the depth. Reputation pays for depth (one per three tables cleared,
capped at 5, and nothing for an immediate quit), and the shelf adds milestones
at five and ten tables. The mode is
deliberately not saved mid-run: it is a score chase, not a tour, so it cannot
be continued into a different session.

### 8.6 THE DAILY LADDER (shared endless)

The Grind card offers two doors. **FREE GRIND** is the personal-record chase
above. **TODAY'S LADDER** is the same endless sequence, seeded by the local
date, so every player meets the same racks today and can compare a score
without an account or a server.

| Rule | Why |
|---|---|
| Base rules: no vault perks, no signed term | Two players must face the same table, not different loadouts. |
| One reputation payout per day | The ladder can be replayed for a better score without becoming a rep farm. |
| Today's best banks on every clear | A closed portal tab still keeps the deepest table reached. |
| A separate ladder streak | Showing up is rewarded, but it never overwrites the daily tour streak. |
| No run save | The ladder is a session score chase and never steals CONTINUE from a parked tour. |

The ladder resets its best at local midnight but keeps the player's streak.
Its rewards are the same one-piece-per-clear build picks as the free Grind;
the only differences are the shared seed and the no-perks rule. The Grind
button on the title carries a dot while today's ladder is unplayed, the same
quiet readiness cue the vault uses for an affordable piece. At the end of a
ladder run, LADDER AGAIN restarts it, FREE GRIND switches to the endless
personal board, and COPY RESULT writes the date, score and depth.

### 8.7 THE HOUSE DUEL (session match)

THE HOUSE DUEL is the title's second front door and the shortest complete
session in the game: one rack, no map, no build, no cash, no shot budget, and
no contract. The player and the House alternate turns; the first to five
pocketed targets takes the table. A pot keeps the cue, a dry shot or scratch
hands it over, and the House keeps shooting while it pots.

| Form | Aim error | Ball in hand | Pockets it can bolt | Reads as |
|---|---|---|---|---|
| I · THE CROUPIER | 0.105 rad | No | 0 | The teaching form. Hide the cue and it must play safe. |
| II · THE SHARK | 0.068 rad | Yes | 0 | It places the cue when blocked and rarely gives a line. |
| III · THE CLOSER | 0.046 rad | Yes | 1 | It punishes the shot you leave, then takes a pocket. |
| IV · THE HOUSE | 0.026 rad | Yes | 2 | Every angle. Every pot closes a pocket. |

The pocket rule is the ladder's authored escalation: the top two forms do not
just aim better, they physically shrink the table the player is shooting into.
A bolted pocket is skipped by physics and by the aim guide, drawn as a brass
plate, and counted in the brief, so the loss is legible.

Beating the highest form reached unlocks the next. Wins, current streak and
best streak persist in local meta; every win pays one reputation, and three
trophies (first win, a five-win streak, and beating Form IV) give the mode a
long arc. A forfeit through the pause card counts as a loss and breaks the
streak. Duels use their own rack seed and their own deterministic House jitter,
so they never borrow — or write — a parked tour's seed, save, build or cash.

### 8.7.1 PASS & PLAY (local match)

The same rack rules with two humans on one device. Player 1 breaks the first
rack and the winner breaks the next; the match is first to five, a pot keeps
the cue, and a dry shot or scratch passes it. A full-screen `PASS THE CUE` card
names the next seat, and `FIRE` becomes `PLAYER n READY`, so a shared keyboard
cannot fire the other player's shot. The series is kept for the session and
shown on the header, the brief and the result card; it is never written to
meta, and leaving through the pause card reads `END MATCH` rather than a
ladder forfeit. This is the portal's couch mode: no account, no second device,
no server.

### 8.7.2 THE HOUSE REMEMBERS (finale grudge)

A normal tour that wins its way past The House teaches it one habit. The next
finale charges a tax on that habit. This is the run-to-run antagonist layer:
the final boss is not a fixed number, it is the player's own last win turned
against them.

| Read | Condition on the winning tour | Finale rule |
|---|---|---|
| THE RAIL TAX | 4+ banked pots | Banked pots pay half. |
| THE LONG NIGHT | Best streak 4+ | One corner pocket opens bolted. |
| THE SPLIT | 2+ multi-ball pots | Multi-ball pots pay 40% less. |
| THE EARLY CALL | 4+ scratches | Phase two starts at a third of the number, not half. |

The read is deterministic (strongest ratio wins, ties go to rails) and is
announced in four places before the player commits: the title ledger, the
route's House card, the boss intro and the live table brief. It applies only
to the final House rack — never the route, the Locksmith, a daily, the Grind
or a duel. Beating the grudge settles it for +2 REP and clears the book
(trophies SETTLED UP and NO READ); losing leaves it in place for the rematch.
A winning tour with no dominant habit writes no read, so a varied build is how
a player stays unpredictable. The read and settlement count persist in meta;
the active snapshot is frozen at run start so a parked run keeps its rule.

### 8.7.3 THE HOUSE'S CHALLENGE (shareable route)

A result used to share a seed nobody could use. Every normal tour now closes
with a compact challenge code, and the title's **PLAY A CODE** card turns that
code back into a run. It is the portal's social layer without an account, a
server or a ghost replay.

| Rule | Behaviour |
|---|---|
| Code | `RR1-<seed>-<TERM>-<stake>`, e.g. `RR1-620122-BANKER-1`. |
| Carries | Route seed, signed term and stake. The recipient's build, vault and House record are their own. |
| Entry | The title's quiet `PLAY A CODE` button opens a paste field; Enter, PLAY CHALLENGE or PASTE starts the route. |
| Parsing | The code may be pasted alone or inside the whole shared sentence; lowercase and surrounding text are accepted. |
| Validation | Seed 1–999999, one of the four signed terms, stake 0–2; anything else stays on the card with a readable error. |
| Scope | Normal tours only. Dailies and the Grind are date/endless modes and never carry a code. |
| Side effect | Starting a challenge replaces a parked tour, and the card says so before the commit. |

The code is a route challenge, not a deterministic replay: two players meet the
same map, term and stake, then build their own answers. That is enough to make
a shared result actionable while keeping the implementation server-free. The
result text stays readable first (`seed`, score, tables, streak) and appends the
code last, so a friend can read the story before choosing to play it.

### 8.8 THE CUE CASE (identity cosmetics)

Six finishes for the stick the player holds, each unlocked by a trophy and
never bought. HOUSE ASH is the default; BRASS & BLACK, OLD IVORY, CARBON, THE
CLOSER and THE HOUSE'S OWN follow from FIRST BREAK, SHARP SHOT, ON A RUN,
HOUSE REGULAR and UNMASKED. The equipped finish is drawn on the felt in every
mode, so a milestone is visible in the core action rather than only on a shelf.

| Rule | Why |
|---|---|
| Earned by trophy, never by reputation | The vault stays the power sink; the case is proof, not a second wallet. |
| Cosmetic only | No finish changes aim, power, score, shot budget or payout. |
| One owner in meta | `cue_finish` is saved beside the trophies; a missing or retired id falls back to HOUSE ASH. |
| Title entry, Escape back | The case is one click from the front door and obeys the same BACK contract as every menu. |

A locked card names the trophy and its live progress (`3 / 5 · ON A RUN`), so
the case reads as a to-do list. The stick is not a fake shop item: the player
starts with HOUSE ASH in hand from the first practice table.

### 8.9 HOUSE CAM (highlight replay)

Every player shot records ball positions at 30 Hz while it rolls. A shot that
pots two targets or pots one off a cushion opens a slow-motion inset in the
top-right of the felt, captioned DOUBLE POT / TRIPLE POT / BANKED POT. The
inset is presentation only:

- it runs for about three seconds on its own clock, beside live play;
- it never pauses the table, blocks FIRE, or changes a score;
- a shot that ends the table skips it, because the reward card is the payoff;
- the camera frames the back half of the shot (minimum 360×180 table units),
  not the full table, so a pot is readable at inset size;
- Settings → House cam replays switches it off, and a new shot dismisses it.

For portals this is the difference between "a pool game" and "a broadcast":
the best moment of a session is celebrated without adding a screen, a wait or
a second input. Recording is capped at 300 frames (ten seconds), and a dry shot
clears the buffer instead of keeping memory alive.

### 8.10 THE HOUSE'S SPOT (position play)

A pool shot has two outcomes: did the target drop, and where did the cue stop?
The base game paid for the first and ignored the second. THE HOUSE'S SPOT is
one brass ring on open felt near the live targets; it moves after every park.

| Rule | Why |
|---|---|
| Pot + leave the cue inside the ring | Position is only paid when the shot also did its job; a dry safety cannot farm it. |
| First park on a table returns one shot | The comeback line: a great leave can rescue a tight rack. |
| Every park pays `SPOT +10` and heat | Position is a score line, not a cosmetic ring. |
| The ring re-rolls after a park | The next leave is a new problem, not a repeat of the same tap-in. |
| Placement is clear of balls, rails, pockets and blocks | A spot the player cannot read or reach is worse than no spot. |
| Duels skip it | The duel already has a pocket race and its own pocket rules. |
| THE HOUSE MARK (tier-2 CONTROL CUE) | Raises the pay to +15 and returns a shot on every park, turning the ring into a build identity. |
| DEAD EYE trophy at eight lifetime parks | The shelf tracks mastery of the new layer. |

The opening table's brief names the ring once; after that the felt label and
the `SPOT xN` line in the HUD carry it. No new screen, no extra confirmation,
no pause: the rule lands in the same aim-and-fire loop as everything else.

For portals this is the difference between a potting toy and a pool game: it
teaches the skill that separates a good player from a great one, and it gives
every shot a second, spatial question with an immediate visual payoff.

## 9. Player Build Systems

### 9.1 Build slots

The initial player has:

- 1 active Cue slot;
- 3 Chalk slots;
- 1 Table Relic slot;
- 0 optional upgrade slots.

After early run progression, the maximum is:

- 2 active Cue slots, with one selected per shot or one passive secondary effect;
- 5 Chalk slots;
- 2 Table Relic slots;
- 1 temporary event slot.

The exact slot unlock timing is a balance variable, but inventory editing must remain constrained. More items should create decisions, not a permanent list of every effect.

### 9.2 Cue design contract

Every Cue has:

```text
cue_id
name
rarity
description
passive_effect
active_effect, if any
tradeoff
tags
upgrade_path
```

Cues primarily affect:

- aim assistance;
- power/spin control;
- cue-ball recovery;
- shot budget;
- reward economy;
- risk management.

They should not directly multiply all score.

Example cues:

- **The Surveyor:** displays one predicted rail rebound; reduces maximum score from direct shots by 5%.
- **The Brake:** improves backspin control; soft shots lose 10% more speed.
- **The House Cue:** grants one extra shot in the first encounter; no bonus after the first region.
- **The Gambler:** increases elite reward quality; scratches cost one additional cash payment.
- **The Locksmith:** once per encounter, reopens a locked pocket; cannot use side-spin during that shot.

### 9.3 Chalk design contract

Every Chalk has:

```text
chalk_id
name
rarity
trigger_event
condition
activation_limit
cooldown_or_reset
payload
visible_counter
text_template
tags
```

A Chalk must answer:

- What event activates it?
- What must the player do to activate it?
- How often can it activate?
- What changes when it activates?
- What is the counterplay or cost?

Chalks may modify:

- score;
- combo meter;
- shot budget;
- cash;
- pocket states;
- ball values;
- contract progress;
- rerolls;
- foul consequences.

They may not silently alter fundamental physics without a clear table indicator.

### 9.4 Table Relic design contract

Table Relics alter persistent table conditions across an encounter or region. They may affect:

- rail behavior;
- pocket value;
- ball archetype frequency;
- initial rack layout;
- marked zones;
- bonus areas;
- encounter selection.

A Relic must be visible on the table or in the active rules panel. Invisible permanent geometry changes are prohibited.

### 9.5 Tags and archetypes

The first build archetypes are:

1. **Banker** — banks, kicks, cushion counts.
2. **Combo artist** — multi-ball chains and caroms.
3. **Spinner** — spin, position, and rail control.
4. **Precision player** — clean direct shots, called pockets, low foul count.
5. **Risk player** — scratches, narrow pockets, and high-value contracts.
6. **Economist** — cash, rerolls, shops, and reward manipulation.

Every launch item should primarily support one archetype and secondarily interact with at least one other archetype.

### 9.6 Synergy rules

A synergy is valid when:

- it can be recognized from the item text;
- it requires a player decision or execution pattern;
- it has at least one counter-strategy;
- it does not make all other builds obsolete;
- it can be tested in the practice table.

Avoid chains that trigger indefinitely. Each event must be processed once per shot, with explicit trigger depth and a maximum of one secondary trigger pass unless an item specifically permits another pass.

## 10. Economy

### 10.1 Currencies

#### Cash

Cash is run-only. It is earned from encounters and spent at shops.

Default cash rewards:

- standard win: `20–35`;
- elite win: `45–75`;
- boss win: `80–120`;
- event outcomes: `-30` to `+60`.

Default shop prices:

- common item: `25–40`;
- uncommon item: `45–70`;
- rare item: `80–120`;
- remove item: `50` initially, increasing by `10` per removal;
- reroll: `15`, increasing by `10` per shop reroll;
- upgrade: `60–100` depending on item rarity.

#### Reputation

Reputation persists between runs. It unlocks content pools, cosmetics, new starting options, and challenge modifiers. It must not simply add permanent score multipliers.

Suggested rewards:

- first-time boss defeat;
- milestone achievements;
- mastery challenges;
- completing a run at a higher stake.

#### Trophy milestones

Twenty-nine persistent trophies form the long-term shelf. Each has one saved
counter, one threshold and one reputation payout, paid once per browser. They
cover first clears, both gates, deep routes, single-shot scores, streaks,
scouted tables, daily streaks, vault ownership, a Stake 2 win, a shut-out House
kill, eight House Spot parks, five/ten-table Grind depths and the three House
Duel feats. Locked cards show live progress (for example `PROGRESS 4 / 6`),
earned cards say COLLECTED, and the title shows `TROPHIES n/29`.

Counters settle at the end of a tour rather than on each shot: a cancelled or
abandoned table can never award a milestone, and a purchase can never quietly
change the price of the thing the player is looking at. Trophies are checked on
the title, map and run summary, and each unlock raises a single toast above the
current screen.

### 10.2 Shop inventory

A normal shop contains:

- three random item offers;
- one service offer;
- one featured item or discounted offer;
- one reroll button;
- a remove option once unlocked.

The shop generator uses weighted rarity and tags, but must avoid presenting three near-identical items unless the shop has an explicit themed rule.

### 10.3 Economy goals

At normal stakes, a competent player should be able to:

- buy one meaningful item every one or two shops;
- afford at least one item before the first boss;
- make a strategic choice between buying now and saving;
- recover from one poor purchase without the run becoming unwinnable.

## 11. Bosses

Bosses are rules puzzles that test adaptability. They must not require one specific item.

### 11.1 Boss template

Every boss defines:

```text
boss_id
signature_rule
phase_count
phase_transition_condition
rack_layouts
shot_budgets
counterplay_hints
reward
```

### 11.2 Initial bosses

#### The House

- Phase one: score 165 on a bank-rich rack; fouls cost an extra shot.
- Phase two at half score: the House takes the table.
- After every player shot that pots nothing, the House takes one shot.
- If it has no line from the cue's lie, it takes ball in hand and places the
  cue where the aim guide shows a clean line (never through a block or ball).
- Each ball it pots bolts one pocket shut (three max). The ball is spotted
  back, so the contract's score ceiling does not shrink.
- Counterplay: pot something every shot and the House never stands. A shut
  pocket is permanent for the rack and visibly removes a scoring route.

#### The Locksmith

- Pockets begin locked.
- Banks and called shots open specific pockets.
- Counterplay: use rails and plan pocket order.

#### The Undertaker

- Once per phase, the highest-value pocketed ball returns.
- A marked “grave pocket” prevents resurrection.
- Counterplay: route important balls to the correct pocket.

#### The Mirror

- The next table rule copies the most recent successful shot tag.
- Repeating the same tag increases its penalty.
- Counterplay: vary shot patterns.

#### The Racker

- After each multi-ball shot, remaining balls are rearranged within a bounded pattern.
- Counterplay: capitalize on combos while they are available, then adapt.

### 11.3 Boss fairness

The boss rule is shown before the encounter begins. Phase changes are announced before they occur. The player must always have at least one viable line that can satisfy the new phase without owning a rare item.

## 12. Failure, Victory, and Rewards

### 12.1 Encounter failure

An encounter fails when:

- the shot budget reaches zero before the contract is satisfied;
- a special failure condition occurs;
- the table becomes invalid and deterministic recovery cannot restore it.

On failure:

- show the final shot evaluation;
- show the missed contract condition;
- show the best available “what to try next” hint only if the player enables hints;
- transition to the run summary with the run marked as lost, unless a previously earned recovery effect changes the result.

There is no random “continue” button in the base mode. Any continuation must be a build effect that was earned and understood before use.

### 12.2 Run victory

A run is won by defeating the final boss. Show:

- final build;
- route;
- score;
- best shot;
- bosses defeated;
- challenges completed;
- new unlocks;
- seed;
- total run time;
- statistics relevant to the player’s style.

### 12.3 Rewards

Rewards should be offered as meaningful choices rather than a fully automatic loot stream. A normal encounter offers three choices drawn from:

- Cue;
- Chalk;
- Table Relic;
- cash;
- upgrade material;
- reroll token.

At least one choice should be immediately usable in most reward screens.

## 13. Persistence and Unlocks

### 13.1 Save data

The save file contains:

- profile version;
- settings;
- key bindings;
- accessibility settings;
- unlocked content IDs;
- completed achievements/milestones;
- statistics;
- current run snapshot, if enabled;
- challenge history;
- last known platform sync state.

A run snapshot must be serializable at planning boundaries. Mid-resolution saving is not required; if the game closes during a shot, it resumes from the beginning of that shot or marks the shot as not taken according to a consistent policy.

### 13.2 Save safety

- Write to a temporary file, flush, then replace the previous save.
- Keep one backup save locally.
- Include schema version and migration functions.
- Never delete an old save because a newer schema cannot be read.
- Steam Cloud conflicts must present both timestamps and allow local/cloud selection.

### 13.3 Unlock philosophy

Unlocks expand possibility rather than increase starting power. Examples:

- new Cue pool;
- new Chalk pool;
- new encounter family;
- new boss;
- new starting loadout choice;
- new stake;
- new visual theme slot once assets exist.

The first run should teach the complete base loop without requiring a grind.

### 13.4 Implemented meta layer: THE VAULT

Reputation is earned by finishing tours (+1 on a loss, +2 on a win, +1 more at
Stake 1 and Stake 2). A daily pays it once per calendar day, so replays are
for score and streak rather than reputation farming.

| Upgrade | Cost | Effect on a normal tour |
|---|---|---|
| THE CUE RACK | 5 REP | Start with THE SURVEYOR (+10 bank, longer rail preview) |
| FELT ALLOWANCE | 9 REP | +1 shot on every table |
| HOUSE CREDIT | 14 REP | 80 starting cash instead of 60 |

Rules:

- Unlocks are read when a new tour starts. A run in progress keeps the
  loadout it began with, including across CONTINUE.
- Dailies ignore all vault upgrades: the shared table is identical for a
  first-timer and a returning player.
- Losing an unlock is impossible; the meta file only grows.
- This is deliberately small starting power, not gated content — the base
  loop is complete on run one, so portals can send a new player straight in.
- The title marks an affordable upgrade, the vault shows progress toward the
  next piece, and the run summary links to it.

### 13.5 Daily challenge

The date is the seed, so every player gets the same route with no server and
no account. Each date also selects exactly one twist from a fixed deck, using
the same seed:

| Twist | Rule |
|---|---|
| RAIL WEEK | Every rail bounce pays +3 |
| DEEP FELT | Bank shots pay +8 |
| SIDE ACTION | Side pockets pay +8 |
| OPENING CREDIT | Start with 80 cash |
| LOOSE FELT | +1 shot on every table |
| OPEN TABLE | Route tables have no blocks |
| CORNER ONLY | Side pockets are closed |
| SLICK FELT | Balls roll longer |

Scoring twists reuse modifiers the game already understands. Table twists
rebuild the rack instead: barriers are stripped, the two side pockets leave the
pocket list, or the felt friction drops. They are applied after each route
table is built, never on a boss (a boss's shape is its identity), and every
table is rebuilt from base rules, so the next normal table can never inherit
one. A CORNER ONLY day removes side-pocket pieces from the reward and shop
pools, because those pieces could never pay that day.

Either kind is applied only inside a daily run, never saved with a normal run,
and is shown on the title card, the map header, the table brief, and the run
summary. The title card also counts down to local midnight, so a player who
has already played knows when the next tour opens. The streak and day's best
live in local meta; reputation from a daily pays once per day.

## 14. Controls and Input

### 14.1 Keyboard and mouse

| Action | Default |
|---|---|
| Aim | Mouse movement / drag |
| Power | Mouse wheel or power slider |
| Spin | Click/drag cue-ball diagram |
| Confirm shot | Left mouse button / Enter |
| Cancel aim | Right mouse button / Escape |
| Inspect rule/item | Hover / Tab focus |
| Pause | Escape |
| Fast resolve | Space after unlock or setting enabled |

### 14.2 Controller

| Action | Default |
|---|---|
| Aim | Right stick |
| Power | Left/right trigger or shoulder buttons |
| Spin | Hold face button and use right stick |
| Confirm shot | A / bottom face button |
| Cancel/back | B / right face button |
| Inspect | D-pad / left stick focus navigation |
| Pause | Menu button |
| Fast resolve | Right shoulder button |

All actions must be represented as named input actions rather than hardcoded device checks. Input rebinding is required before release.

### 14.3 Input rules

- Confirm is disabled when power is below the minimum.
- A shot can be canceled indefinitely during planning.
- Input is ignored or routed to the result overlay during resolution.
- The game never interprets accidental stick drift as a confirmed shot.
- The last-used input device determines prompt style, but mouse and controller remain usable.

## 15. UI and Information Architecture

### 15.1 Encounter HUD

The encounter HUD contains:

- contract title and progress;
- current score and target;
- shots remaining;
- cash and run resources;
- active table rules;
- active Cue and Chalks;
- spin control;
- power control;
- confirm/cancel prompts;
- optional event feed.

The table remains the largest and most important visual element.

### 15.2 Information priority

When information competes for space, preserve it in this order:

1. table geometry and balls;
2. contract and shots remaining;
3. current aim/power/spin;
4. active rule consequences;
5. build trigger states;
6. score breakdown;

- plain-language effect;
- trigger condition;
- current counter/progress;
- remaining activations;
- tags;
- one example;
- known conflicts with active table rules.

- Practice Table;
- Unlocks/collection;
- Settings;
- Controls/rebinds;
- Accessibility;
- Credits;
- Pause;
- Run summary;

Use a screen stack: pause overlays the encounter, settings overlays pause, and Back always returns to the previous screen without boolean-state combinations.

- 1920×1080;
- 2560×1080 ultrawide;

- short UI sound hook;

- final-pocket emphasis;

## 18. Technical Gameplay Contracts

### 18.1 Simulation boundary

The billiards simulation accepts an immutable `ShotInput` and a starting `TableState`, then returns a `ShotResult` and ending `TableState`.

```text
ShotInput + TableState + Ruleset + Seed
  → deterministic simulation
  → ShotResult + TableState + event list
```

Rendering, UI, audio, and Steam services consume the result. They do not change it.

### 18.2 Required game states

The gameplay state machine includes:

```text
BOOT
TITLE
PROFILE_LOADING
RUN_SETUP
MAP
ENCOUNTER_INTRO
ENCOUNTER_PLANNING
SHOT_RESOLVING
SHOT_RESULT
REWARD_SELECTION
SHOP
EVENT
BOSS_INTRO
RUN_SUMMARY
PAUSE
SETTINGS
```

Invalid transitions must be rejected. For example:

- a shot cannot be confirmed from the map;
- rewards cannot be selected while balls are moving;
- a shop cannot be opened while an encounter is resolving;
- a run cannot be silently overwritten by starting a new run.

### 18.3 Data-driven content

Cues, Chalks, modifiers, encounters, bosses, rewards, and map nodes must be represented as data assets with stable IDs.

No gameplay content should require editing a central switch statement to add a new item. New effect types may require code, but existing effect types must be composable through data.

### 18.4 Event-driven UI

Gameplay emits events such as:

```text
run_started
encounter_started
shot_started
ball_contacted
rail_contacted
ball_pocketed
foul_committed
scratch_occurred
shot_resolved
chalk_triggered
score_changed
contract_progressed
encounter_won
encounter_lost
reward_offered
run_won
run_lost
```

The HUD listens to events and updates only when relevant state changes. It must not poll the simulation every frame to calculate score or contract state.

### 18.5 Performance target

The game targets a stable 60 FPS or better on supported Steam Deck hardware and ordinary desktop hardware. Since the game is mostly turn-based, simulation correctness is more important than extreme visual complexity.

Do not create or destroy large numbers of objects during every shot. Use reusable presentation objects for ball effects, score popups, and table feedback.

### 18.6 Steam adapter

Steam functionality must be behind an interface with an offline implementation:

```text
SteamAdapter
  initialize()
  is_available()
  set_achievement(id)
  write_stat(id, value)
  upload_leaderboard_score(id, score)
  sync_cloud_save()
  open_overlay()
```

The editor and offline builds must use a local mock. Gameplay must not depend on Steam being available.

## 19. Determinism, Seeds, and Replays

### 19.1 Seed rules

A run seed determines:

- map layout;
- encounter selection;
- rack generation;
- reward offers;
- shop inventory;
- event outcomes;
- procedural modifier choices.

The player’s shot input is never randomized after confirmation. Random-looking physics must result from deterministic simulation.

### 19.2 Random number streams

Use separate named streams for:

- map generation;
- encounter generation;
- rewards;
- shops;
- events;
- cosmetic presentation.

Cosmetic randomness must not consume gameplay RNG values.

### 19.3 Replay support

At minimum, log:

- seed;
- version/build ID;
- content database version;
- each starting state checksum;
- each `ShotInput`;
- each result checksum.

A replay should be able to identify when a future content or physics change makes it invalid.

## 20. Balance Framework

### 20.1 Balance objectives

At normal stake:

- a new player should usually reach the second region after learning the controls;
- a competent player should occasionally reach the final boss;
- an expert should win through multiple archetypes;
- no single item should be required for victory;
- no common item should be stronger than a rare item in every context;
- direct shots should be reliable but lower ceiling;
- banks, combos, and positional play should offer higher ceiling with higher execution risk.

### 20.2 Testing metrics

Track during playtests:

- shots per encounter;
- average score per shot;
- foul rate;
- scratch rate;
- contract completion rate;
- item trigger rate;
- reward pick rate;
- shop purchase rate;
- route choice rate;
- win rate by build tag;
- win rate by stake;
- time spent planning versus resolving;
- player-reported cause of failure.

### 20.3 Dominant strategy checks

An item or archetype is suspect when:

- it appears in more than 60% of successful high-stake runs;
- it is picked regardless of route or encounter type;
- it has no meaningful counterplay;
- it makes its intended risk irrelevant;
- it creates infinite or near-infinite resource loops.

Fix dominant strategies by adding tradeoffs or counters before simply reducing their numerical values.

### 20.4 Economy checks

At normal stake, a run should not require perfect shop luck. A player who wins ordinary encounters should have enough cash to make several meaningful choices, but not enough to buy everything.

If players frequently finish runs with large unused cash, shops are not offering sufficient meaningful sinks. If players never reach a shop with enough cash to buy anything, rewards or prices are wrong.

## 21. Tutorial and Onboarding

The first play session teaches the game in this order:

1. Aim and confirm a direct shot.
2. Adjust power.
3. Pocket a second ball in one shot.
4. Observe cue-ball position after contact.
5. Use a bank shot.
6. Inspect a Chalk trigger.
7. Choose a reward.
8. Visit a shop.
9. Read a table modifier.
10. Complete an encounter with a modified rule.
11. Reach the first elite.
12. Understand the first boss before playing it.

The tutorial should never introduce more than one new rules concept in a single required shot.

The shipped first table carries a three-step coach on the lower cushion: aim,
then power, then fire. It names one action at a time, ticks off as the player
performs it, and retires permanently the moment a shot is fired, so it never
becomes a modal the player has to dismiss. It also appears on practice and on
a first daily table, because it only changes local UI and cannot affect a
shared seed. HOW TO PLAY remains the reference for everything after it.

The opening table is deliberately the easiest clear in the game: three pockets
on a six-ball procedural rack with ten shots. Tables two and three stay on
pocket clears (four pockets by table three) before introduced rules such as
combo, bank-count and no-scratch appear. A 95-point score contract on the
first rack used to end most first sessions; score asks on later procedural
racks are now capped against the live value of that rack.

A practice table should provide:

- reset rack;
- free placement of balls after unlock or in tutorial mode;
- selectable Cue/Chalk loadout;
- shot history;
- toggleable aim guide;
- repeat-last-shot option;
- no permanent progression impact.

## 23. Autonomous Development Responsibilities

The primary developer is responsible for implementing and maintaining:

- the core simulation;
- the encounter state machine;
- scoring and contracts;
- Cues, Chalks, Relics, and bosses;
- map generation;
- economy and rewards;
- local persistence and migrations;
- UI and input behavior;
- controller support;
- Steam integration;
- deterministic seeds and replay diagnostics;
- automated tests;
- balance tooling;
- placeholder art/audio integration points;
- performance and compatibility fixes;
- build/export configuration;
- technical documentation;
- release checklists.

External asset work may supply:

- final visual art;
- final animation;
- music;
- sound effects;
- voiceover;
- branding and marketing assets.

The codebase must therefore expose stable integration points for external assets:

- semantic asset IDs;
- documented import dimensions and formats;
- animation/event names;
- audio event names;
- fallback assets;
- no gameplay behavior hidden inside a final art asset;
- no required audio cue for understanding a rule.

When external assets are unavailable, development continues with generated or placeholder content. The gameplay cannot be blocked by waiting for art or music.

Autonomous development does not mean silently changing the game’s core contract. Changes that affect any of these require explicit design review:

- shot rules;
- scoring formula;
- run length;
- persistent progression power;
- launch scope;
- multiplayer or monetization;
- visual/audio direction that affects gameplay readability.

The implementation agent may make ordinary engineering decisions autonomously, including refactoring, test strategy, data organization, UI layout refinement, performance optimization, and placeholder content creation, as long as this document’s player promise remains intact.

## 24. Non-Goals for the First Release

Do not add these before the core game is proven:

- real-time multiplayer;
- online matchmaking;
- complicated character RPG stats;
- dozens of currencies;
- fully realistic tournament rules;
- procedural 3D table destruction;
- deck construction before a run;
- permanent raw damage/score inflation;
- mandatory daily challenges;
- extensive narrative branching;
- cosmetic monetization;
- physics tricks that cannot be previewed or explained.

These may be reconsidered after the core loop has demonstrated strong replayability.

## 25. Definition of “Fun Enough to Continue”

The vertical slice is not complete merely because it functions. It passes the design gate when playtesters can do all of the following without coaching:

1. Explain the encounter objective.
2. Intentionally attempt a direct shot and a bank shot.
3. Identify why a shot earned its score.
4. Use cue-ball position to influence a future shot.
5. Choose between a safe shot and a high-value risky shot.
6. Understand at least one Chalk synergy.
7. Make a route choice based on risk and reward.
8. Recover from a miss without feeling cheated.
9. Name a different build they want to try.
10. Start another run after losing.

The strongest success signal is not that players win. It is that after losing, they immediately describe a different build, route, or shot pattern they want to test.

## 26. Open Variables for Playtesting

These values are intentionally implementation-tunable:

- ball friction and restitution;
- aim-guide precision;
- shot resolution speed;
- shot budget by encounter tier;
- score target bands;
- cash rewards and prices;
- slot unlock timing;
- rarity distribution;
- number of active item triggers per shot;
- boss phase thresholds;
- default stake difficulty;
- amount of cue-ball recovery assistance;
- amount of deterministic preview information.

Changing an open variable is allowed if the change is recorded in the balance log and tested against the design pillars. A numerical adjustment must not be used to conceal a rules problem that needs a clearer mechanic or better UI.

The implementation order is:

1. Create the project and input actions.
2. Implement a resolution-independent table coordinate system.
3. Implement deterministic balls, rails, and pockets.
4. Implement aim, power, spin, and shot confirmation.

8. Implement fixed authored Scenario Tables with barriers and zones.

10. Implement data-driven Chalk effects.
11. Implement rewards and a minimal run state.
12. Implement map routing.
13. Implement shops and economy.
14. Implement one two-phase boss using Scenario Table modules.
15. Implement save/load and seed reproduction.
16. Implement controller-first UI navigation.
17. Add Steam adapter and platform services.
18. Expand content only after the vertical slice passes the fun gate.

The first playable build should contain no permanent progression, no large content library, and no final asset dependency. It should prove the shot loop, the score loop, and one build synergy before anything else.
